else: not a test run, not a consumer change, not a rollout.

## 1. Versioning

The contract version is independent of the design-system lockstep version (which governs packages
and images, not documents). A contract change bumps the contract version:

- MAJOR: a removed or tightened requirement, or a newly mandatory behavior for an existing consumer.
- MINOR: backward-compatible additions only (optional guidance, a new consumer).
- PATCH: clarifications.

A later change to the drawer rules in `packages/css/src/site.css` requires a contract version bump.
This is a rule for reviewers; CI does not enforce it in this version.

## 2. Terms and provenance

Provenance tags are those defined in `docs/evidence/web-contract-evidence.md` section 1: `[CODE]`
pinned inspected source; `[CONFIG]` GitOps desired state; `[LIVE]` authenticated ArgoCD or
anonymous HTTP observation; `[PREVIEW]` isolated preview. `unknown (not observed)` is stated with a
reason. Status values used in this document:

- `observed`: asserted by an executed check (for design-source rows, by an existing Storybook play function).
- `not-run`: not executed. It is never a pass.
- `not-applicable`: proven absent in pinned source only. No row uses it in version 1.0.0.
- `exception (EX-n)`: the consumer mechanism cannot meet the requirement; see section 8.

PASS is not a status in this document. The keywords MUST, SHOULD and MAY follow RFC 2119.

Ownership split `[CODE]` (`packages/css/src/site.css`, comment above `.mctl-site-burger`): "The CSS
owns the look only. The consumer owns the behaviour." `site.css` supplies the shared drawer visuals;
this contract specifies the behavior. No consumer is required to use a common component, element ID,
class name, state attribute or script. `data-nav-open` and `.mctl-site-burger` are the `site.css`
hook for consumers that opt into the shared drawer visuals, not a mandate.

Implementation claims about a consumer are pinned to a full 40-character commit SHA or an immutable
link. No consumer source was readable when this version was written, so every consumer mechanism,
selector and breakpoint below is `unknown (not observed)`: the consumer repositories were not
cloned, and the evidence report (section 2) states the same.

## 3. States

- `desktop`: inline navigation visible; the toggle is absent or inert.
- `narrow-closed`: toggle visible; the panel is not visible and not in the Tab order or the
  accessibility tree.
- `narrow-open`: panel visible; its links are reachable.

The boundary `B` between `desktop` and the narrow states is a site-owned input (section 5).

that use the shared drawer; any equivalent mechanism that yields the observable outcome satisfies
the requirement. Evidence for every row is `[CODE]` unless stated.

## 6. Behavioral equivalents per consumer

For every consumer: mechanism and selectors are `unknown (not observed)` (consumer source not
read, no pinned SHA). CSP context is `[LIVE]` from evidence section 4. Route classes: `landing`,
`content`, `app-shell`, `sensitive` (section 9).

### 6.1 mctl-web (Nuxt/Vue)

- Mechanism: unknown (not observed). Expected: a router `afterEach` hook or equivalent meets HDR-10;
  server-rendered output keeps HDR-16.
- CSP context: `script-src 'self' 'unsafe-inline'` plus listed hosts. No change to it is recommended.
- Route classes: `landing`, `content`. `mctl.ru` 301-redirects to `mctl.ai` and inherits these rows.

### 6.2 mctl-docs (VitePress DefaultTheme)

- Mechanism: framework-native hamburger is accepted as the mechanism; no class, ID or
  `data-nav-open` is demanded. Whether it meets HDR-8, HDR-9 and HDR-12 is unknown (not observed).
- Conditional exception EX-3 applies only if pinned source or a preview run shows a gap.
- CSP context: `script-src 'self'` plus hashes (37 hashes, list not preserved in the evidence report).
- Route classes: `content`, `landing`.

### 6.3 mctl-telegram (Go server, CSS checkbox public chrome, no forced JS)

- Mechanism: a CSS checkbox toggle per the issue; unknown (not observed) in pinned source.
  A checkbox reports checked or unchecked, not expanded or collapsed, and a `<label>` is not a
  button. It is not treated as equivalent to a button: see EX-1 and EX-2.
- The owner may choose progressive enhancement from a `'self'` script (already permitted by
  `script-src 'self' 'unsafe-inline'`) instead of accepting the exceptions. Not decided here.
- CSP context: `default-src 'none'`, `form-action 'self'`. Tracker: telegram#599.
- Route classes: `landing`, `sensitive` (connect, manage, OAuth lite).

### 6.4 mctl-academy (Vue/Hono)

- Mechanism: unknown (not observed). `B = 981px` per issue #209 (`--drawer-wide`).
- Tracker: academy#210 for asset supply.
- CSP context: `script-src 'self' https://stats.mctl.ai`.
- Route classes: `landing`, `content`, `app-shell` where present.

### 6.5 mctl-alice (local native JS)

- Mechanism: unknown (not observed). `B = 981px` per issue #209.
- CSP constraints (noted, not changes): `style-src 'self'` means `site.css` must be vendored locally;
  `script-src-attr 'none'` means handlers must be attached from a `'self'` script, not inline attributes.
- The design-source story named "Static HTML recipe (alice, seerrsense)" shows an inline nav with no
  burger; whether these sites now use the burger is unknown (not observed).
- Route classes: `landing`, `sensitive` (OAuth).

### 6.6 seerrsense (local native JS)

- Mechanism: unknown (not observed). `B = 768px` per issue #209.
- CSP context: no CSP header returned on the landing page `[LIVE]`. Adding one is an owner decision
  outside this contract.
- Route classes: `landing`, `sensitive` (consent, error).

## 7. Adoption notes

A consumer meets a requirement by the mechanism of its runtime. Nothing in this contract requires
loosening a CSP, adding a remote script or adding a shared header script; every requirement can be
met inside each site's current CSP.

## 9. Route classes and sensitive routes

- `landing`, `content`, `app-shell`: anonymous or signed-in chrome checked on isolated previews.
- `sensitive`: Telegram connect, manage and OAuth lite; Alice OAuth routes; SeerrSense consent and
  error routes. Their header cases are verified only from `[CODE]` and isolated `[PREVIEW]`
  fixtures, never by production authentication probes.
- No verification step may loosen a CSP, add a remote script or add a shared header script.

## 12. Roles, gates, rollout and rollback

Roles: contract owner (mctl-design maintainers); site owner per consumer (each site's repository
owner); epic owner (mctlhq/.github#330); test-infrastructure owners (design#14, design#34). Related
trackers: telegram#599, academy#210, design#78. No new issue is opened by this document.

Gates, independent and in order:

- G0 contract approval: this document, digest-bound owner approval. Authorizes nothing else.
- G1 Preview Assurance execution: runs layers 1 and 2; no production change. Separate from G0.
- G2 per-consumer adoption: the site owner; exceptions signed off.
- G3 per-consumer release: the site owner's own release process.

Each consumer rolls out and rolls back alone: rollback is reverting that site's own change. The
contract and `site.css` are untouched by a consumer rollback.
